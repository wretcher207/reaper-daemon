Give the agent the desk.

Reaper Daemon lets Claude Code, Codex, Cursor's terminal agent, and any MCP client operate a running REAPER session over plain local files. It reads the project, moves transport, edits FX and routing, writes humanized drum parts, and proves its changes with before-and-after measurements.

Capabilities

The whole desk, addressable by name.

An agent discovers what a project actually contains, then acts on tracks, FX, and parameters by their real names. No fixed plugin list, no hardcoded instrument knowledge.

  • Project control

    Transport, tempo, cursor position, time selection, project save. Render exists too, kept behind a config gate until you switch it on.

    play · stop · set_tempo · save_project

  • Tracks & routing

    Add, delete, rename, reorder, select, color. Volume, pan, mute, solo, arm. Read sends, receives, and parent bus; create sends with one command.

    add_track · set_track_volume · create_send

  • FX & automation

    Load, bypass, reorder, or remove any plugin. Set parameters by formatted value like "-16.00 dB", resolved against the plugin's own display scale. Write parameter automation envelopes.

    scan_fx · add_fx · set_fx_param · write_fx_param_automation

  • Markers, regions & media

    Create and edit markers and regions, place and move media items, read the timeline back as data the agent can reason about.

    get_markers · get_items

  • MIDI & drums

    Insert MIDI files straight onto tracks, or compose grooves in a small drum language with humanization baked in at render time.

    insert_midi_file · groove · jam

  • Discovery first

    One call dumps every FX chain and parameter in the project. Tracks and FX come back with stable GUIDs, because names can duplicate and indices move when you edit a chain.

    get_context · scan_fx · get_fx_parameters

How it works

No servers. No sockets. Files in a folder.

The bridge is one Lua script living inside REAPER, talking to agents through ordinary files. That is the entire moving part, which is why it works with everything and trusts nothing to chance.

  1. 1

    The agent publishes a command

    A JSON file written to a temp name, then renamed into inbox/. The rename is atomic, so the bridge never sees half a command.

  2. 2

    The bridge executes it live

    A deferred loop polls four times a second, runs one command per tick through the native REAPER API, and stamps a heartbeat so agents can tell alive from busy from dead.

  3. 3

    The result lands where it can be read

    JSON replies appear in outbox/. Command files move on to archive/ or failed/, bounded by retention. A stale command from a crashed session is refused at startup rather than replayed into a project that moved on.

The same protocol powers two front doors: reaperd.py, a single-file CLI with subcommands for every workflow, and reaper_mcp.py, a stdio MCP server exposing 24 tools to Claude Desktop, Claude Code, or any MCP client. Both are plain Python 3. Nothing to install, no pip packages, no build step.

Measured proof

ok means REAPER did it.
Verified means you can hear it.

Every command returns success, but success is not sound. The closed-loop pair captures a track, makes the change, then captures the exact same spot again and reports what actually moved in the audio.

Captures are frozen once, before the mutation, so a moved cursor cannot skew the comparison. If either capture comes back silent, verify refuses a verdict instead of comparing dead air. When a fallback capture is not an isolated track, the report says so rather than presenting full-mix numbers as per-track evidence.

exit 0
Verified. Both captures clean and comparable, deltas reported.
exit 1
Refused. Nothing was mutated, because the pre-capture was blocked or silent.
exit 2
Unverified. The change may already be live. Agents are taught not to blindly retry; one Ctrl+Z reverts it.

Push it further with tune_param: name a measured target like "bass LUFS-I down 3 dB" and it iterates the parameter, rendering between attempts, until the number is hit or honestly reports that it was not. With Post Mortem installed, agents also get true peak, spectrum, stereo image, and masking tables to diagnose with.

The drum workflow

From guitar riff to humanized take.

A complete pipeline for programmed drums that don't sound programmed: analyze the material, build the beat from the riff up, render it with a drummer's hands, and drop the MIDI into your kit.

  1. 01Profile the song

    profile reads a guitar stem bar by bar: onset density, timing regularity, palm-mute versus ringing decay, silence, low/bright balance, and a 16th-note accent grid. It proposes section boundaries and repeat groups. You correct the labels; the machine does the counting.

  2. 02Kicks off the riff

    riff reads the take's transients into a kick grid at three attack strengths, anchored to the item's grid. Kicks land where the guitar picks, not where a preset thinks they should.

  3. 03Write it in DSL

    Grooves are small step grids, not sample-menu orders. Accents, ghosts, and flams are single characters. Fills are lanes that ramp across the kit.

  4. 04Insert, humanized

    groove renders the grid through a velocity model with fatigue, weak-foot, timing jitter, hand alternation, and cymbal choke behavior, then drops standard MIDI onto your drum track.

Any drum library, discovered on the spot

The engine ships knowing GM Standard plus maps for RS Monarch, Odeholm, MDL Tone, and Sleep Token II. For anything else, discover-map reads the note names your drum library already installed and classifies them into roles: kick, snare, hats, rides, crashes, china, toms. Sparse kits fall back gracefully instead of breaking the render. Libraries without note names get a map by hand, once, with add-map.

Trust & control

It works for you. You keep the last word.

An agent with its hands on your session should earn trust the way a good assistant engineer does: previewing changes, staying reversible, and asking before anything destructive.

  • Everything is one undo away

    Every mutation runs inside a REAPER undo block. Single commands and whole batches each land as one step, so Ctrl+Z takes it all back at once.

  • Preview before commit

    Dry-run mode resolves targets, applies selectors, and returns the exact result payload without touching state. Agents are documented to reach for it when a target is uncertain.

  • Risky operations stay gated

    Render, project save, and audio capture do nothing until you explicitly flip allow_risk_level_3 in the bridge config. Off by default, and it stays off until you say otherwise.

  • Destructive means confirmed

    Commands that delete ask the calling model to carry intent, and batches support stop-on-error so a failed step halts the rest instead of plowing through your session.

  • Identity you can rely on

    Discovery returns REAPER's real track and FX GUIDs alongside names. Plans built on GUIDs survive renames and chain edits; plans built on names get verified first.

  • An honest boundary

    This is a local file channel for a single-user studio machine. Anyone who can write to the folder can drive REAPER, and an optional shared-secret token guards against accidental writers. Keep the folder local; that is the boundary, stated plainly. No network listener exists to harden.

Compatibility

If it can write a file, it can run the session.

Claude Code Claude Desktop Codex Cursor terminal agent Any MCP client Plain CLI & raw JSON files

Point an MCP client at it

One registration line and the whole bridge shows up as 24 conversational tools, from transport control to the closed-loop verify pair:

claude mcp add reaper -- python3 /path/to/reaper-daemon/reaper_mcp.py

Then just ask: "what plugins are on the master?", "carve 2 dB out of the bass at 300 Hz", "program a d-beat at bar 33".

Or let any agent drive the CLI

Codex, Cursor, and shell-capable agents skip MCP entirely and use the same commands you would. Identical behavior on macOS, Windows, and Linux, with exit codes as the contract:

python3 reaperd.py status
python3 reaperd.py fxload "Pro-Q 3" Bass
python3 reaperd.py setparam Bass "Pro-Q 3" "Gain" "-2.5 dB"
python3 reaperd.py verify Bass -- set_fx_param '...'

Fuzzy plugin queries resolve against REAPER's installed cache before anything loads. Parameter values binary-search the normalized range until the plugin's own display agrees.

Install

Three ways in. None of them heavy.

Requires REAPER and Python 3.8 or newer. That is the entire dependency list: no packages to install, no account, no license server.

Fastest The one-liner

macOS, Linux, or Git Bash on Windows. Clones the repo, wires auto-start into REAPER's startup script, done. Idempotent, safe to re-run.

curl -fsSL https://raw.githubusercontent.com/wretcher207/reaper-daemon/main/install.sh | bash

Manual From a clone

Full control and the complete toolset including the drum engine. Restart REAPER after wiring.

git clone https://github.com/wretcher207/reaper-daemon.git
cd reaper-daemon
python3 setup/install.py   # python on Windows

In REAPER Via ReaPack

Import the repository under Extensions › ReaPack, then browse for Reaper Daemon. ReaPack keeps the bridge script itself updated; the CLI and drum engine still come from a clone.

https://github.com/wretcher207/reaper-daemon/raw/main/index.xml

Prove it's alive

With REAPER open and a project loaded:

python3 reaperd.py status
python3 reaperd.py send commands/examples/get_context.json --wait

Status reports the bridge heartbeat. The second command prints a JSON description of your open session. Full command reference lives in bridge/command_schema.md.
